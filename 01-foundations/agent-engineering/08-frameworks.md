# 第 8 章：框架实战与取舍

## 学习目标

知道框架抽象替你承担了什么、隐藏了什么；能把同一条简单流程映射到自写实现和候选框架，基于需求而非热度选型。

## 定义、原理与设计原因

Agent 框架通常把模型客户端、Prompt、工具注册、执行循环、状态/检查点或 RAG 组件封装成可组合的 API。抽象的设计目的是减少重复接线、统一生命周期，并让常见编排更易实现；代价是引入依赖、学习曲线、隐式默认行为和版本迁移成本。

框架不是质量保证：同一框架仍可能生成错误答案、执行不安全工具或无法解释失败。选型时先明确要解决的工程问题，再用一个固定任务进行小型对比；检查调用链能否追踪、测试是否容易、权限如何接入、状态是否能恢复、依赖是否持续维护。了解框架概念时区分 Java 应用层（如 Spring AI / LangChain4j）与偏编排/图状态的框架，不以名称相似推断能力等同。

## 常见面试考察方向（非频率统计）

1. **为什么使用 Agent 框架？什么时候不用？**答题线索：复用接入、编排和状态能力；流程简单时直接 API/普通代码更清晰，避免无必要抽象。
2. **如何比较两种框架？**答题线索：同一任务、同一数据和验收指标；比较控制流透明度、错误处理、持久化、测试、观测、安全接入、部署、维护与迁移成本。
3. **使用框架后哪些职责仍在应用？**答题线索：身份授权、业务规则、数据隔离、预算、失败策略、评估和审计仍由应用负责。

## 比较维度

在 Spring AI、LangChain、LangGraph、AgentScope 等课程提及的框架间，比较：语言与团队技能、模型接入、工具生命周期、状态持久化、流式体验、检查点/恢复、可观测性、权限集成、测试难度、部署和版本稳定性。不同框架定位和能力不完全相同；表中名称是候选调查对象，不是推荐结论。

可以先按抽象层理解这些名字：Spring AI 连接 Java/Spring 应用与模型/向量/工具；LangChain 提供较高层的模型、工具与 Agent 组合；LangGraph 更强调显式状态、节点和控制流编排；AgentScope 是包含 Agent、工作流和多 Agent 协作能力的框架。官方资料将 LangGraph 定位为面向有状态、长运行任务的底层编排运行时；这些定位和 API 会演进，选型前查当前版本官方文档。[LangChain](https://docs.langchain.com/oss/python/langchain/overview)、[LangGraph](https://docs.langchain.com/oss/python/langgraph/overview)、[AgentScope](https://doc.agentscope.io/)。

应用框架像 Spring 容器与编排组件：可减少样板，但不会自动让 Prompt 正确、工具安全或评测有效。要能沿着调用链追到原始 API，并知道框架版本如何影响行为。Java 主线按现有路线优先验证 Spring AI；不要把多套框架同时铺成主线。

## 实践与验收

先用不超过两个工具实现小流程，再用一个候选框架实现同一行为。固定输入和验收标准，比较代码量、可观测性、错误处理、状态恢复、测试难度和依赖复杂度。保存版本号、配置和原始结果。选型报告必须说明未解决问题和迁移成本，而非只写“功能丰富”。

## 动态信息边界

框架版本、API、许可证、维护和安全状态可能变化。开始实现时核对官方文档、发布记录和依赖信息，并记录访问日期；仓库已有资料索引仅作为入口，不替代当日核验。

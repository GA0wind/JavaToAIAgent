# 第 5 章：工具、MCP 与 Skill

## 学习目标

能设计边界清楚的工具契约，解释 Tool Calling、MCP 和 Skill 分别解决的问题，并选择按需加载能力的方式。

## 定义、原理与设计原因

- **Tool**：由应用暴露给模型选择的有限操作，包含名称、说明、参数 Schema 和返回结构。模型提出调用，应用验证后执行。
- **MCP**：Host 与外部 Server 发现和使用能力的协议。典型角色为 Host 管理用户体验与授权，Client 管理连接，Server 暴露 Tools、Resources、Prompts。协议便于不同宿主复用集成；它不替代后端 API，也不自动授予用户权限。
- **Skill**：课程图中的可复用任务说明/能力说明，按需提供给模型或 Agent。具体格式和执行行为依产品而异，不能把 Skill 本身等同于可安全执行的沙箱。
- **人工确认**：在具有副作用的动作前展示对象、参数和影响，并把确认绑定到待执行的具体操作。

工具说明把机器接口翻译成模型可选的“动作目录”；Schema 降低格式错误，但业务规则仍需服务端校验。只读、相互独立的调用可能适合并行；有副作用的并行调用会产生竞争、部分成功和重复执行问题，需控制并发、幂等和审批。MCP 的价值在跨应用复用能力时更明显；单一应用内的本地函数直接调用可能更简单。

## 常见面试考察方向（非频率统计）

1. **Tool Calling 与 MCP 有何区别？**答题线索：前者是模型提出结构化动作的交互机制；后者标准化应用如何发现/连接外部能力。两者可组合，也可分别使用。
2. **MCP 的 Host、Client、Server 和 Tools/Resources/Prompts 各是什么？**答题线索：分别说明应用容器、协议连接组件、能力提供端，以及操作、数据上下文和模板能力。
3. **工具 Schema 校验通过是否代表可以执行？**答题线索：不代表；还要认证、授权、租户/数据范围、业务规则、幂等、副作用和审计检查。
4. **哪些工具调用可并行，哪些要人工确认？**答题线索：独立无副作用操作可评估并行；写操作按风险配置审批，确认内容应和实际执行参数绑定。

## 工具契约

工具描述要写清用途、何时调用、何时不调用、参数含义和副作用。输入 Schema 负责结构校验，业务服务负责身份、权限、数据范围、幂等和规则校验。返回尽量简短、结构化且包含状态。模型输出的参数和工具结果都是不可信输入。并行调用只适用于彼此独立且允许并发的只读或安全任务；写操作要谨慎处理重复执行与部分成功。

Java 对照：工具不是可以随意调用的 RPC 代理，而是一个受策略控制的应用服务入口。工具最好薄，领域规则仍留在领域服务。

## MCP 与 Skill

- **MCP**标准化 Host、Client、Server 间发现和访问能力的协议边界。它可连接 Tools、Resources、Prompts，但不会自动解决用户授权、租户隔离或下游安全。
- **Skill**在课程图中代表可按需加载的任务说明或能力包；不同产品的 Skill 格式和执行机制可能不同。应把其内容视为不可信输入，核验来源、权限和可执行动作。
- 普通函数调用是应用内直接集成；当需要跨宿主复用或标准化连接时，再判断 MCP 是否带来足够收益。

## 实践与验收

设计一个只读工具 `searchSyntheticRunbook`，写出说明、Schema、用户权限来源、查询边界、超时、错误返回和审计字段。再画 MCP Host → Client → Server → 服务层的关系，并说明不使用 MCP 的直接调用方案。若实践 SDK，记录实际协商协议版本与传输方式。

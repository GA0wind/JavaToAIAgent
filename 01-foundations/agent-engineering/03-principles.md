# 第 3 章：够用的模型原理

## 学习目标

掌握能指导应用设计的原理：Token 如何影响容量和费用、上下文窗口为何不是记忆、Embedding 解决什么问题、生成模型为何可能给出无依据答案。

## 定义、原理与设计原因

- **Token**：某个模型 Tokenizer 将输入编码后得到的离散单位；可能是字、子词、字节片段或特殊标记，不等于固定的汉字/单词。
- **上下文窗口**：模型单次处理的输入与输出 Token 容量。消息历史、工具定义、检索结果和输出预算共同占用它；它不是持久化存储。
- **Attention**：序列中的位置按 Query/Key 相似度聚合 Value 信息。因果语言模型用遮罩避免读取未来 Token；KV Cache 可复用已有 Key/Value，故不能简单说每步都从头重算全部历史。
- **Embedding**：把文本或其他对象映射为向量以便计算相似性。语义相近不代表事实相同，也不能替代权限判断。
- **幻觉**：模型生成了流畅但缺乏可靠依据或错误的内容。模型学习的是生成规律，生成过程不等于调用权威事实校验器。

子词 Tokenizer 的设计在词表规模与序列长度之间折中：字符级词表小但序列长；整词级表示直观但词表容易膨胀、难覆盖新词；BPE 等方法从基础符号学习常见片段合并。Token 数因此影响上下文利用、推理工作量和按量计费，但耗时/成本不与 Token 数简单一比一，需结合具体架构、缓存和提供商计量。

长上下文提高可容纳信息量，但模型未必能均匀利用每个位置；检索、排序、压缩、来源标记和评估是把有限上下文用于当前任务的工程手段。内部推理 Token 是否暴露由模型服务决定，不能把不可见的内部过程当作可审计证据。

## 常见面试考察方向（非频率统计）

1. **Token 是什么，为什么不能用 `String.length()` 估算？**答题线索：Token 是模型专属编码单位；Tokenizer、语言和文本格式影响切分，字符长度与 Token 数不是同一计量单位。
2. **上下文窗口和会话记忆有什么区别？**答题线索：窗口是单次请求容量，记忆是应用持久化与检索策略；历史需显式选择并重新放入请求。
3. **Embedding 相似度能否证明两个文本事实相同？**答题线索：不能；向量用于召回/排序，需用原文、来源、权限和规则核验。
4. **为什么长上下文不一定解决 RAG？**答题线索：容量大不保证召回相关、位置利用、引用正确；长输入还增加噪声、成本和延迟，应比较检索与上下文策略。

Token 专题学习材料见 [Token 与分词器笔记](../llm-basics/token-and-tokenizer.md)。注意力、上下文窗口和 Embedding 的部分按本章及官方资料学习。

## 核心概念

- **Token 与分词器：**模型处理的是 Token 序列而非 Java 字符。词元可能是字、子词或字节片段；语言、格式和分词器都会影响数量。`String.length()` 不能当作 Token 计数器。课程链接的第 2 P 专讲 Token，后续可按分集目录继续分词器和 BPE。
- **上下文窗口：**一次模型请求能处理的输入与输出序列容量。历史消息、系统提示、工具定义、检索资料和预留输出都可能占预算；它不是自动持久化的会话存储。
- **长上下文：**容量更大不等于所有位置都能同等有效地利用。应以目标模型和任务评估长资料策略，避免把“中间遗忘”说成所有模型固定规律。
- **Embedding：**把文本映射为向量表示以支持相似度检索。语义相近不保证事实相同，向量相似度也不能代替权限或业务过滤。
- **生成与推理：**模型输出由训练与推理机制产生；“思考 Token”或内部推理信息是否可见取决于模型服务。应用不应依赖未公开的内部过程来证明答案正确。
- **幻觉：**输出流畅不等于有证据。用可核查来源、拒答/澄清策略和评测来降低风险。

## 实践与验收

准备短文本、长历史、重复指令、缺少资料四组虚构输入。用目标提供商的官方 Token 计数方式或实际 usage 字段比较预算，并记录上下文裁剪策略。设计一个无证据问题，要求系统指出缺失信息而不是猜测。保存原始脱敏结果和方法限制。

# 第 9 章：评测与可观测

## 学习目标

把“效果不错”转成可复现的质量检查；通过结构化 Trace 找到问题发生在检索、模型、工具还是系统环节。

## 定义、原理与设计原因

- **评测集**：带输入、期望行为/答案要点、证据和评分规则的一组固定用例。
- **Recall@K**：相关证据中有多少至少进入前 K 个检索结果；它衡量召回，不直接衡量最终答案质量。
- **Faithfulness / 忠实度**：回答主张是否能由给定上下文支持；需明确定义评分范围和标注规则。
- **LLM-as-a-judge**：用模型按规则辅助评分。它扩展检查规模，但可能有偏差、评审不稳定或偏好特定表达，应抽样人工复核。
- **Trace**：用 Trace ID 串联一次请求的模型调用、检索、工具、重试和最终结果；Metrics 聚合延迟、错误率、Token 用量等数据。

评测把主观体验变成固定对照：先留基线，再每次改一个关键因素，重跑相同用例并检查逐例变化。CI 门禁应区分确定性硬约束（Schema、权限、工具参数、预算、拒绝非法动作）与生成质量评分；对波动性答案可使用阈值、抽样或离线回归，避免单个评审分数决定所有发布。观测让评测发现的失败能追到具体阶段，同时需脱敏并控制 Trace 的访问、保留和字段基数。

## 常见面试考察方向（非频率统计）

1. **Recall@K 与回答正确率有什么区别？**答题线索：Recall@K 只看相关资料是否被召回；答案还要看证据是否支持、模型是否正确理解、引用是否准确。
2. **如何证明一次 Prompt 或检索修改有效？**答题线索：固定数据集、评分、模型/参数、环境和基线；对比逐例变化并查看退化样本，报告样本范围及限制。
3. **LLM-as-a-judge 能替代人工吗？**答题线索：适合规模化辅助，不应独自评判安全/业务硬规则；用人工标注校验一致性、偏差和评分标准。
4. **Trace 中应该记录什么？**答题线索：关联阶段、耗时、状态、检索/工具摘要和模型用量；敏感原文、凭据和高基数标签默认不采集。

## 评测设计

- 建立小而人工核验的代表性数据集，覆盖常见输入、边界、无答案、矛盾资料和工具失败。记录数据来源、期望证据与评分规则。
- RAG 可测 Recall@K、MRR 或 NDCG 等检索指标；答案侧可测正确性、引用支持度、拒答质量。工具 Agent 可看工具选择、参数合法性、执行结果和任务完成率。
- 自动评分器或 LLM-as-a-judge 可扩展检查，但要对照人工抽样、检查偏差并固定评分提示及模型版本。单个总分掩盖失败类型。
- 每次 Prompt、模型、索引或流程变更跑回归集；保留基线、差异、失败样本和环境配置。

## Trace 与指标

为一次任务关联 trace ID，按跨度记录模型请求、检索候选、工具调用、重试与最终结果。记录延迟、错误率、Token 使用和估算费用；脱敏并设置访问和保留规则。OpenTelemetry 等追踪标准能帮助统一观测数据，但具体语义和 SDK 接入按版本核对。禁止把敏感提示、凭据或整份私有文档原文作为默认日志。

OpenTelemetry（OTel）是用于生成、收集和导出 traces、metrics、logs 等遥测数据的可观测性框架/工具集，本身不是存储和看板后端。Trace 表示一次请求跨组件的因果链，由父子 Span 组织；Metrics 用聚合数值监控趋势；Logs 记录事件并可通过 Trace ID 关联。采用标准化接口与 Collector 有利于更换后端和跨服务关联；仍需控制采样、数据脱敏和高基数标签。[官方概览](https://opentelemetry.io/docs/what-is-opentelemetry/)。

## 实践与验收

为一个只读问答任务写 10 条人工核验虚构问题，包含无答案和冲突项；建立基线，改一次检索设置再回归。验收材料包括数据集版本、评分说明、逐例差异、失败分类和 Trace 样例。小样本仅用于练习，不宣称普遍性能提升。

# 第 1 章：基础入门

## 学习目标

能够区分“使用 Agent”和“开发 Agent”，画出一次请求中用户、应用、模型、工具、外部数据之间的边界，并判断任务该用普通模型调用、固定工作流还是 Agent。课程路线强调用一个项目逐章加能力；本仓库沿用既定的 Loan Platform Engineering Copilot 作品集框架，不声称已实现。

## 定义、原理与设计原因

- **LLM**：根据输入序列生成下一个 Token 的模型。它能做语言理解和生成，但回答本身不是经过业务数据库或事实系统验证的结论。
- **Agent 应用**：把模型、上下文、工具、应用控制逻辑、状态与安全边界组合起来的系统。所谓“自主”是应用允许模型在有限动作集合中选择下一步，不意味着模型自己拥有系统权限。
- **Workflow**：主要路径和状态转换由程序预先定义；中间可以调用模型。它易测试、易审计，适合步骤确定的业务过程。
- **Tool Calling**：模型按照工具说明返回一个结构化动作请求；服务端校验后执行实际代码，再把结果交回模型。

为什么这样分层：语言模型擅长处理模糊自然语言，传统程序擅长确定性规则、数据读取和权限执行。分工后既能利用模型的语言能力，也能保留后端系统的可预测性。若任务路径固定，Workflow 通常比开放式循环更简单；只有当下一步确实需要根据新信息动态选择时，才引入 Agent 决策。

## 常见面试考察方向（非频率统计）

1. **Agent、Workflow、普通聊天和 RAG 有什么区别？**答题线索：聊天描述交互方式；RAG 是补充外部证据的方法；Workflow 是控制流程；Agent 将部分下一步选择交给模型。它们可组合，分类要看控制权和数据流。
2. **什么场景不需要 Agent？**答题线索：固定步骤、规则明确、不能容忍模型自由选择、或普通模型调用足以完成时，优先使用确定性代码或 Workflow。
3. **Agent 中模型和应用各负责什么？**答题线索：模型理解请求、生成内容或提出动作；应用管理身份、上下文、工具执行、授权、预算、状态和结果校验。

## 概念与 Java 对照

- LLM 是生成组件，不是完整应用；Agent 是包含模型决策、状态、工具执行和停止条件的应用流程。
- 工具是受控的后端能力，模型只能提出调用建议，服务端负责校验和执行。
- 工作流像显式状态机或编排流程，步骤和分支由代码确定；Agent 把部分下一步选择交给模型。
- 先写出用户任务、输入、可用证据、允许动作和失败出口，再选架构。不要因“Agent”这个名称就默认采用自主循环。

## 实践

以虚构的“查询产品说明并核对模拟工单状态”需求为例，画出当前（无模型）流程和目标流程。标出哪些环节需要模型理解自然语言，哪些环节必须确定性处理，哪些数据只能在权限检查后读取。记录不做事项，例如自动修改工单或做授信判断。

## 验收与证据

- 一张组件/时序图，含信任边界及失败路径。
- 一页需求说明，列出用户、成功条件、非目标和待确认项。
- 能口头解释为什么固定、可预测的业务步骤优先用 Workflow。

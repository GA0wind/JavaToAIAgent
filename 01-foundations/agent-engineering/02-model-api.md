# 第 2 章：模型 API

## 学习目标

能说明一次对话请求的消息结构和生命周期，区分角色、内容、工具调用、流式片段与最终结果；实现时能约束结构化响应，并对提供商差异作适配。

## 定义、原理与设计原因

- **消息**：带角色和内容的输入项。应用按顺序构造消息；角色语义、优先级、工具消息格式由具体 API 约定。
- **流式输出**：服务端逐块返回响应。应用需要识别开始、分片、完成、失败和取消，不能把每个分片当成完整 JSON 或最终答案。
- **采样参数**：temperature、top_p 等改变候选 Token 的抽样分布。它们控制输出变化，不验证事实，也不是确定性开关。
- **结构化输出**：以 Schema 或格式约束模型返回可解析的数据，再由应用做类型、范围、业务规则和权限校验。

这些接口设计为消息、流和结构化格式，是为了让应用明确表达对话上下文、减少大段文本传输等待，并将输出连接到后端 DTO/流程。流式更快展示首段内容，但带来部分响应、取消和中途失败处理；Schema 提高格式可控性，却不能保证字段值正确。统一 Java 适配层适合收敛超时、错误和日志，同时不应假装各厂商参数完全一致。

## 常见面试考察方向（非频率统计）

1. **多轮 API 如何表示对话？**答题线索：按 API 定义构造有序消息；应用明确管理历史和角色，不能默认模型自动记住之前的请求。
2. **流式输出和普通输出的工程差异？**答题线索：流式改善首字体验，但需处理分片、断连、取消、部分 JSON、工具参数累积和最终状态。
3. **temperature 越低是否越准确？结构化输出是否可信？**答题线索：采样参数不等同于事实准确率；Schema 主要约束格式，仍要做业务校验和授权。

## 核心知识

- 对话 API 常把输入表示为有序消息。`system`、`developer`、`user`、`assistant`、工具结果等角色名称和优先级随 API 规范而异，不能假定不同服务的协议完全一致。
- 流式响应是分片传输过程。分片可能是文本、工具调用参数或元数据；应用需要累积、处理取消、连接中断和最终完成状态。
- temperature、top_p 等采样参数用于调整生成分布，不是正确性旋钮。仅发送当前模型支持的参数。
- 结构化输出需要 Schema、解析和语义校验。JSON 能解析不表示字段值可信或业务规则成立。
- 统一适配层应收敛超时、错误映射、日志字段和重试策略，同时保留提供商特有能力的明确边界。

## Java/Spring 实践

选定一个兼容的模型服务和固定依赖版本，做一个最小服务：普通问答、流式回答、一个 JSON Schema 响应。API Key 通过环境变量注入，不能写入配置文件或日志。为请求记录模型标识、耗时、状态和可用的 Token 用量，不记录敏感原文。

使用合成请求测试正常结果、空响应、格式错误、超时、限流和客户端取消。将传输层错误与模型语义错误分开处理。

### 结构化材料抽取的边界

材料预审可以让模型从非结构化文本中提取字段，但应让结果带有原文证据片段或页码，并允许“未找到/需人工确认”。随后由确定性代码检查类型、必填项、范围、格式和字段间规则；冲突或高影响结果交由人工复核。这样利用模型理解多种表述的能力，同时避免把概率性生成当成权威业务判定。模型自报的 confidence 不能单独作为通过条件。

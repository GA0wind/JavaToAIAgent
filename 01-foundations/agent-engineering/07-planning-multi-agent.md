# 第 7 章：规划与多 Agent

## 学习目标

能按任务可预测性选择 ReAct、Plan-and-Execute 或固定工作流，设计可恢复状态，并判断多 Agent 拆分是否值得其通信和协调成本。

## 定义、原理与设计原因

- **ReAct**：让模型在生成决策、执行动作和读取观察之间迭代。观察结果会作为新上下文影响下一步。
- **Plan-and-Execute**：先生成任务计划，再由执行器按步骤运行；可在步骤结果变化时检查或修订计划。
- **多 Agent**：由多个有边界的角色/执行单元协作完成任务；增加协作角色本身不必然增加正确性。
- **Checkpoint**：保存任务状态与已完成步骤，使进程中断后能恢复；恢复语义要包含外部工具动作的执行状态。

动态规划适合步骤不完全可预定的探索任务；固定图/工作流更适合高约束流程。多 Agent 的拆分依据应是可独立验证的子任务、不同上下文/工具或确实可并行，而不是追求“更智能”的架构。持久化需处理幂等：超时可能代表结果未知，恢复时应查账本/业务状态，不可简单重放写操作。

## 常见面试考察方向（非频率统计）

1. **ReAct 与 Plan-and-Execute 的区别？**答题线索：前者边观察边决定，后者先形成计划再执行；两者都需校验计划/动作、限制预算和处理中断。
2. **什么场景适合多 Agent？**答题线索：子任务边界明确、并行收益或隔离上下文可量化；同时评估协作开销、冲突、失败传播和可观测性。
3. **Agent 中断后怎样恢复而不重复副作用？**答题线索：持久化状态/检查点、调用 ID、幂等键和结果状态；对未知结果先核查再决定继续。
4. **状态图是不是模型思维过程？**答题线索：不是；它是应用定义的可执行状态和转换，可用于控制、恢复与观测，不代表模型内部推理的完整表示。

## 选择范式

- **固定 Workflow：**路径已知、约束强、审计要求高；由代码规定节点及转换。
- **ReAct：**需要根据工具观察逐步决定下一步；必须限制循环步数、耗时和工具权限。
- **Plan-and-Execute：**先形成计划再逐项执行，适合步骤较多但可分解的任务；计划需要校验，执行中应允许重新规划。
- **多 Agent：**仅当子任务边界清楚、并行可带来收益或需不同专门上下文时考虑。要处理共享状态、冲突、失败传播和成本。

## 状态与检查点

对每个步骤定义输入、输出、前置条件、重试规则和完成状态。持久化任务 ID、检查点、工具调用状态及结果引用。恢复时区分“未执行”“已成功”“执行结果未知”；外部请求超时不代表写操作没有发生。为写动作使用幂等键或状态核查。状态图是流程约束和可观测结构，不等同于模型的隐式思考。

## 实践与验收

为虚构值班问题设计“搜资料→查模拟状态→汇总建议”的状态图。比较固定图与允许模型选下一步的版本。注入工具超时、返回冲突、进程中断和重复请求。验收要求：恢复不重复已完成的写动作；失败能定位；模型不能绕过审批。此练习默认只读，不连接真实系统。
